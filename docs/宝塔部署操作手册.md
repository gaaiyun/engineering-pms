## 发布顺序

1. 生产数据库冷备与 `quick_check`。
2. 在生产冷备副本上启动当前 hooks/migrations，跑权限与事务验收。
3. 更新 PocketBase hooks/migrations 并重启 systemd。
4. 验证健康、登录、读写、Realtime、任务事务和日志。
5. 构建并发布 Web。
6. 构建、安装并验证 APK。
7. 如采用 `/pb` 反代，确认 Web/APK 全链路后再关闭公网 8090；3.06 当前因 APK 真机待验收而保留。

任何一步失败，停止后续发布并恢复冷备或上一版静态文件。

## PocketBase 基线

```bash
cd /www/server/pocketbase || exit 1
./pocketbase --version
systemctl status pocketbase --no-pager -l
curl -fsS --max-time 5 http://127.0.0.1:8090/api/health
sqlite3 -readonly pb_data/data.db 'PRAGMA quick_check;'
```

要求：版本 `0.22.21`、systemd `enabled/active`、业务库为 `ok`。服务账户建议为 `pocketbase:pocketbase`，可执行文件和 migrations/hooks 由 root 管理，`pb_data` 由服务账户读写。

## 冷备

```bash
cd /www/server/pocketbase || exit 1
test "$(df -Pk . | awk 'NR==2 {print $4}')" -gt 5242880 || exit 1
systemctl stop pocketbase
ss -lntp | grep ':8090' && exit 1 || true
stamp=$(date +%Y%m%d_%H%M%S)
mkdir -p "maintenance_backups/$stamp"
cp -a pb_data "maintenance_backups/$stamp/pb_data"
sqlite3 -readonly "maintenance_backups/$stamp/pb_data/data.db" 'PRAGMA quick_check;'
```

必须先确认备份文件数量、大小和 `quick_check`，再改生产文件。

## 部署 hooks 与 migrations

只上传本次 diff 中经过审查的文件，不整目录覆盖，不上传本地 `pb_data`、测试数据库或 Key。

先比对生产迁移记录与待发布文件：

```bash
sqlite3 -readonly pb_data/data.db 'SELECT file, applied FROM _migrations ORDER BY applied;'
find pb_migrations -maxdepth 1 -type f -printf '%f\n' | sort
```

同一环境可能由早期分支产生不同文件名但创建了相同集合。发现历史分叉时，只复制经过人工审查、尚未应用的新迁移；禁止用仓库整个 `pb_migrations` 替换生产目录。迁移启动失败时先恢复冷备，再分析冲突，不通过改名或删除 `_migrations` 记录强行继续。

```bash
chown root:root /www/server/pocketbase/pb_hooks/*.js /www/server/pocketbase/pb_migrations/*.js
chmod 0644 /www/server/pocketbase/pb_hooks/*.js /www/server/pocketbase/pb_migrations/*.js
deploy_started_at=$(date '+%F %T')
systemctl restart pocketbase
systemctl is-active pocketbase
curl -fsS --max-time 5 http://127.0.0.1:8090/api/health
journalctl -u pocketbase --since "$deploy_started_at" --no-pager
```

日志门禁必须从本次部署的准确开始时间读取，避免旧故障日志触发错误回滚；日志中不得出现 migration 失败、`ReferenceError`、`database disk image is malformed` 或事务 Hook 错误。

## 临时 SSH 发布密钥

无法复用图形 SSH 客户端会话时，可为一次发布创建独立临时密钥。私钥只能保存在本机受控目录，公钥只追加到服务器 `authorized_keys`，发布结束后按注释精确撤销，不复制已有密钥，也不把密钥、口令或完整授权文件写入仓库和交接文档。

Windows PowerShell 调用 OpenSSH 时，`ssh-keygen -N '""'` 在部分环境会生成以两个引号为真实口令的密钥。无口令临时密钥应通过交互方式连续提交两次空输入，随后先验证：

```powershell
ssh-keygen -y -f '<private-key-path>' | Out-Null
ssh -i '<private-key-path>' -o IdentitiesOnly=yes -o BatchMode=yes root@<server-host> 'echo SSH_OK'
```

只有两条命令都无需输入口令且成功时，才用于无人值守发布。

## systemd

仓库模板：`deploy/pocketbase/pocketbase.service`。安装前按实际路径审阅：

```bash
install -m 0644 deploy/pocketbase/pocketbase.service /etc/systemd/system/pocketbase.service
systemctl daemon-reload
systemctl enable --now pocketbase
```

自动恢复验收：

```bash
old=$(systemctl show pocketbase -p MainPID --value)
kill "$old"
sleep 10
new=$(systemctl show pocketbase -p MainPID --value)
test "$new" != "$old"
curl -fsS --max-time 5 http://127.0.0.1:8090/api/health
```

不要同时使用 `nohup`、宝塔进程守护和 systemd 管理同一进程。

## 可选 `/pb` 反向代理

反代不是功能发布的前置条件，但 HTTPS Web/App 推荐使用。配置片段位于 `deploy/pocketbase/nginx-pb.conf`。

修改宝塔站点配置前先复制备份，只有 `nginx -t` 成功才 reload。验证：

```text
https://<server-host>/pb/api/health
https://<server-host>/pb/_/
```

Web 使用同源 `/pb`；APK 必须在构建时显式写入完整生产 URL。全部验证通过后才把 PocketBase 监听改为 `127.0.0.1:8090` 并关闭安全组公网 8090。3.06 APK 尚未完成真机验收，当前不能执行关闭操作。

## Web 发布

```powershell
Set-Location frontend
$env:npm_config_cache = 'G:\dev-cache\npm'
$env:VITE_PB_URL = 'https://<server-host>/pb'
npm ci
npm test -- --run
npm run build
```

上传 `frontend/dist` 内容到新的时间戳目录，校验后原子切换站点目录或软链接。不要在生产目录直接解压覆盖一半。

发布后检查 `/`、`/login`、`/app`、`/my-tasks`、`/my-projects`、`/notifications`、`/me` 和 `/system/users` 深链。

## 私有生产数据

- 真实员工账号通过系统用户管理或 `deploy/private/` 下的忽略脚本维护。
- 同步必须幂等：按 username 查找，存在则更新姓名/角色/启用状态，不存在才创建。
- 初始密码不写入 Git、文档、日志或命令历史；首次登录后修改。
- LLM Key 只在“系统管理 -> AI 配置”录入，不经浏览器 localStorage、Vite 环境变量或静态文件。

## 回滚

- Web：切回上一版静态目录。
- hooks/migrations：停服务，保留失败现场，恢复发布前冷备后启动。
- `/pb`：恢复 Nginx 备份，`nginx -t` 后 reload；必要时暂留公网 8090。
- 不使用 `git reset --hard`、直接覆盖 `data.db` 或边运行边复制 WAL 数据库回滚。
